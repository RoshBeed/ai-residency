Frontend (LoadBalancer -- Docker Desktop binds this to localhost automatically):

  kubectl get svc frontend -n {{ .Release.Namespace }}
  open http://localhost:{{ .Values.frontend.servicePort }}

Backends are ClusterIP-only, so only the frontend reaches them. To reach one from your machine
for debugging, port-forward it. They all listen on 8000, so forward one at a time (or pick a
different local port per shell):
{{- range $name := (keys .Values.backends | sortAlpha) }}
{{- $svc := index $.Values.backends $name }}
{{- $port := $svc.containerPort | default $.Values.backendDefaults.containerPort }}
  kubectl port-forward -n {{ $.Release.Namespace }} svc/{{ $name }} {{ $port }}:{{ $port }}
{{- end }}

Two endpoints, two meanings. `/health` says the process is up and always answers 200.
`/ready` says this pod can actually serve, and answers 503 until its weights are loaded --
which is what keeps an unusable pod out of its Service's endpoints. A pod showing 0/1 READY
for a long time is reporting honestly; check what it says:

  kubectl exec -n {{ .Release.Namespace }} deploy/<name> -- \
    python -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8000/ready').read())"

Check status:

  kubectl get pods -n {{ .Release.Namespace }}

Scheduling: the backends' memoryRequest values sum to roughly 21GiB across
{{ add (len .Values.backends) 2 }} pods. Compare that against what this node will actually give you --

  kubectl get node -o jsonpath='{.items[0].status.allocatable.memory}'

-- because if it is short, some pods sit Pending rather than the whole set crash-looping over
scarce memory. That is the requests doing their job. Free room for a Pending pod with:

  kubectl scale deploy/<name> -n {{ .Release.Namespace }} --replicas=0
