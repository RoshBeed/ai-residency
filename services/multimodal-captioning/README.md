# Image Captioning — Bridging a Frozen CLIP Vision Encoder to a Frozen Qwen3 Language Model

## TL;DR

- **What it is:** image captioning via a small trainable adapter bridging a frozen CLIP vision encoder to a frozen Qwen3 language model (the LLaVA/PaLiGemma recipe).
- **What's built:** the full pipeline — data loading, adapter training with a held-out baseline, checkpointing, and a served inference path (FastAPI + Streamlit) — runs end to end, with four trained checkpoints shipped and comparable.
- **Where it gets to:** the shipped adapter closes **19.2% of the gap** between an untrained adapter (0.1848 CLIP agreement) and human captions (0.3233), scored on held-out Flickr30k pairs.

This repo has two parts: a warm-up exercise doing zero-shot image classification with CLIP, and
the main project — an image captioning model I built the way LLaVA and PaLiGemma do it: freeze a
large pretrained vision encoder and a large pretrained language model, and train only a small
adapter in between that translates image embeddings into the language model's embedding space.
The vision side is CLIP ViT-B/32 [1], the language side is [Qwen3-0.6B-Base](https://huggingface.co/Qwen/Qwen3-0.6B-Base),
and only the adapter's ~1.58M parameters ever receive a gradient.

## 1. Introduction

[The ViT classifier](https://github.com/RoshBeed/ai-residency/tree/main/services/vit-classifier) built a Vision Transformer from
scratch and trained the whole thing end to end on MNIST. That works when the target task is small
and cheap to supervise. It doesn't work when the target task is "describe any photo in fluent
English": there's no dataset large enough to teach both vision and language from scratch cheaply,
so I went with transfer learning instead: reuse two models that already understand their
respective modalities (CLIP already understands images, Qwen3 already understands language), keep
both frozen, and learn only the small piece that translates between them.

**Figure 1.** CLIP's own Figure 1 [1]: contrastive pretraining on image/caption pairs (left), then
reusing the trained encoders for zero-shot classification by turning class names into prompts
(right) — build a "dataset classifier" out of text embeddings, then pick the highest-scoring one for
a new image.
![CLIP paper Figure 1 — contrastive pre-training, dataset classifier construction, and zero-shot prediction](assets/fig1-clip-contrastive-pretraining.png)

Part 1 of this repo (`multimodal_captioning/zero_shot.py`) *is* the right-hand half of this diagram, almost exactly:
`data/images/` stands in for "New image," the ten class names become `"a photo of a {label}"`
prompts, and `argmax` over the cosine similarities picks the label. See Figure 8 for what that
produces on the real 10-image set. That's classification, where the output is one label out of a
known set. Captioning is harder: the output is free-form text, generated by an autoregressive
language model, which raises the actual question this project answers. Given a frozen vision
encoder and a frozen language model, how do you actually connect them?

## 2. System Architecture

## 3. Method

### 3.1 Two Ways to Bridge a Vision Encoder to a Language Model

There are two established patterns. The original Transformer decoder [2] — and this repo's own
[the ViT seq2seq service](https://github.com/RoshBeed/ai-residency/tree/main/services/vit-seq2seq) — uses **cross-attention**:
a dedicated attention layer inside the decoder that attends to the encoder's output at every
generation step. LLaVA [4] and PaLiGemma [3] use something simpler: project the image into the
language model's embedding space and **concatenate** it as if it were just another token, then let
ordinary self-attention do the rest. No architectural change to the language model at all.

**Figure 3.** Cross-attention (`xAtt`, left) versus self-attention concatenation (`sAtt`, right) as
a vision-language bridge.
![Cross-attention vs self-attention bridge diagram](assets/fig2-cross-attention-vs-concat.png)

The left half is the original Transformer decoder / the vision transformer project's seq2seq pattern: the encoder's patch
features feed a dedicated `xAtt` layer inside the decoder at every generation step. The right half
is what this repo actually builds: the image features get folded straight into the decoder's input
sequence, and ordinary self-attention (`sAtt`, no architectural change to the decoder at all) does
the rest. I took the second path. It's the cheaper option in every sense that matters here: no
change to the language model's architecture, no cross-attention weights to initialize or train, and
the only new parameters are whatever sits between the vision encoder's output dimension and the
language model's embedding dimension.

**Figure 4.** PaliGemma [3] — the reference architecture this design borrows most directly: a
frozen contrastive vision encoder, a linear projection, and a frozen decoder LM.
![PaliGemma architecture diagram — SigLIP vision encoder, linear projection, Gemma decoder](assets/fig3-paligemma-architecture.png)

This repo's Section 3.2 adapter follows this same shape (frozen vision encoder, projection, frozen
decoder LM), just with a different encoder/decoder pair:

### 3.2 This Repo's Adapter

The actual implementation swaps PaliGemma's SigLIP/Gemma pair for CLIP ViT-B/32 and Qwen3-0.6B-Base,
and swaps the single linear projection for a slightly deeper adapter:

```python
def build_adapter(clip_dim, qwen_dim, *, final_layer_norm=False):
    layers = [
        nn.Linear(clip_dim, qwen_dim),  # 512 → 1024
        nn.LayerNorm(qwen_dim),
        nn.GELU(),
        nn.Linear(qwen_dim, qwen_dim),  # 1024 → 1024
    ]
    if final_layer_norm:
        layers.append(nn.LayerNorm(qwen_dim))
    return nn.Sequential(*layers)
```

`final_layer_norm` is there because one of the three shipped checkpoints was trained with a
trailing `LayerNorm` and the other two weren't. Every checkpoint records which shape produced it,
so the loader reads the architecture off the artifact instead of guessing.

**Figure 5.** This repo's captioning architecture: CLIP's patch grid → adapter → 49 soft tokens →
Qwen3 decoder.
```mermaid
flowchart LR
    img["Image"] --> clip["CLIP ViT-B/32<br/>encoder (frozen)"]
    clip --> grid["50 x 768<br/>CLS + 49 patches"]
    grid --> drop["drop CLS<br/>post_layernorm"]
    drop --> proj["visual_projection<br/>49 x 512 (frozen)"]
    proj --> adapter["Adapter<br/>1.58M params (trainable)"]
    adapter --> scale["x 0.0302<br/>match embedding scale"]
    scale --> soft["49 soft tokens<br/>49 x 1024"]
    cap["Caption tokens"] --> embed["Qwen3 embeddings (frozen)"]
    soft --> concat["concat"]
    embed --> concat
    concat --> qwen["Qwen3-0.6B-Base<br/>(frozen)"]
    qwen --> out["Caption"]
```

With the dimensions filled in: CLIP ViT-B/32 cuts a 224px image into a 7x7 grid, so its encoder
returns 50 tokens — a CLS summary and 49 patches. The adapter reads **the 49 patch tokens**, not
the CLS summary, so the language model sees where things are in the frame rather than one vector
for the whole image. Each is projected to 512 by CLIP's own frozen `visual_projection`, mapped to
Qwen3's 1024-dim embedding space by the trainable adapter, and concatenated in front of the
tokenized caption before the frozen decoder runs.

Reading the patch grid costs 49 decoder positions per image instead of one, which is most of the
training cost here — the backward pass runs through the frozen decoder over that sequence.

**Soft tokens have to arrive at the scale of real token embeddings.** The adapter ends in a
LayerNorm, so whatever it emits has unit variance. Qwen3's embedding table has a standard
deviation of 0.0302, so an unscaled adapter hands the decoder vectors 33 times larger than any
token it was pretrained on. Nothing errors; the decoder is simply driven off-distribution, and the
cheapest repair available to the adapter is to stop varying with the image at all. That is
measurable: before the fix, training *halved* the adapter's per-image spread, to 0.104 against an
untrained adapter's 0.227, and every image drew the same caption. The last line of
`image_soft_tokens` multiplies by the embedding standard deviation, measured once when the
backbones load, so the checkpoint stays a plain `nn.Sequential` and nothing has to be relearned.

### 3.3 Training: A Captioning Loss That Only Scores the Caption

Training only updates the adapter: CLIP and Qwen3 stay in `eval()` with `requires_grad = False`.
For a batch of (image, caption) pairs, the image is turned into 49 soft tokens, the caption is
tokenized, the two are concatenated, and the labels at all 49 image positions are set to `-100` so
PyTorch's cross-entropy loss ignores them. The model is never asked to "predict" the image, only to
predict caption tokens conditioned on it. The mask has to widen with the image sequence: leave it
at one position and the model is trained to emit 48 image vectors as if they were words.

**Figure 6.** The training signal, end to end.
```mermaid
flowchart LR
    flickr[("Flickr30k<br/>image + caption pairs")] --> img["Image"] --> adapter["Adapter"] --> imgtok["49 image tokens<br/>(labels = -100, ignored)"]
    flickr --> cap["Caption"] --> captoks["Caption tokens<br/>(real labels)"]
    imgtok --> seq["[49 image tokens, caption tokens]"]
    captoks --> seq
    seq --> qwen["Qwen3 (frozen)"]
    qwen --> loss["Cross-entropy loss<br/>on caption tokens only"]
    loss -.gradients.-> adapter
```

## 4. Implementation

Mapping the architecture from [Section 2](#2-system-architecture) onto the actual file layout:

```
config/__init__.py        Config(BaseConfig) and the CHECKPOINTS registry — model names, prompt,
                          sample size, learning rate and every path, in one dataclass
multimodal_captioning/    The captioning package
├── data.py               FlickrDataset, the seeded train/held-out split, and the batching collate_fn
├── models.py             Frozen CLIP + Qwen3 loading (Backbones), build_adapter, load_adapter
├── training.py           train(config): baseline, epoch loop, best-checkpoint save, W&B + Hub
├── captioning.py         generate_caption(image) — the repo's one inference path
└── zero_shot.py          Part 1: CLIP zero-shot classification, no training and no adapter
serving/api.py            FastAPI: POST /caption (base64 image in, JSON out), GET /health
checkpoints/
├── adapter.pth                    10 Flickr30k pairs / 3 epochs at 1e-5 — 30 steps, barely off init
├── adapter_trained.pth            10 local images / 20 epochs, one- and two-word captions
└── adapter_flickr_batched.pth     100 Flickr30k pairs / 3 epochs, batch size 8 — best of the three
data/images/             10 sample photos (cat, dog, horse, bird, car, person, tree, house, book, phone)
tests/test_multimodal_captioning.py   Tests for the adapter, data pipeline, and serving path
pyproject.toml / uv.lock Dependencies, lint/type config, and a CPU-only torch index
```

The modules live in the `multimodal_captioning/` package, run as `python -m
multimodal_captioning.training` and so on, with `config/` and `serving/` alongside it — no
import-path juggling and no `sys.path` manipulation anywhere. It didn't used to be. `src/` was three
flat scripts that reached for each other through whatever happened to be on the import path,
`ui/app.py` patched `sys.path` at runtime because `streamlit run` only puts `ui/` on it, and there
was no configuration layer at all: model names, the prompt, the sample size, the learning rate and
three checkpoint file names were literals scattered across those scripts and eleven notebook cells,
with the same value written differently in different places.

Shared behaviour — device selection, logging, checkpoint format, seeding, Hub upload and W&B
tracking — comes from [`libs/common`](https://github.com/RoshBeed/ai-residency/tree/main/libs/common), pinned by tag, so it
is defined once for the whole portfolio instead of reimplemented per repo. Checkpoints carry their
own architecture metadata via its `extra` field, so the loader always knows what shape to expect.

A `Makefile` wraps the commands below so the common paths are one line each:

```bash
make install       # uv sync — creates .venv from pyproject.toml/uv.lock
make zero-shot     # Part 1 — CLIP zero-shot classification, ~10 seconds, no GPU needed
make train SERVICE=multimodal-captioning         # Part 2 — fit the adapter on Flickr30k
make serve SERVICE=multimodal-captioning         # FastAPI backend, POST /caption, at http://localhost:8000
make notebook      # open notebooks/notebook.ipynb
make test SERVICE=multimodal-captioning          # run the test suite
make check         # lint + typecheck + tests
make help          # list every target
```

**On the training data.** Every other artifact this portfolio trains on is mirrored under
`roshbeed/` so no stage depends on an account outside the project, and Flickr30k is the one
exception. Its authors do not hold copyright in the images: use is governed by Flickr's own Terms
of Use, and the data is offered at their link for non-commercial research and education, with no
redistribution right. So `config.dataset_name` points at `nlphuji/flickr30k`, a community
re-upload, and training here depends on that staying put. Serving does not — the adapter is the
only thing this service trains, and it lives under `roshbeed/` with the rest.

`make serve SERVICE=multimodal-captioning` runs the FastAPI backend, matching every other repo in this portfolio; the CLIP demo
is `make zero-shot`. The API itself is a thin wrapper around the same `generate_caption()` the
unified frontend in `services/frontend` calls.

`make train SERVICE=multimodal-captioning` writes to `checkpoints/adapter_flickr_batched.pth`, which is the committed checkpoint
the API and the frontend load by default. Running it overwrites that file. Point `checkpoint_dir`
or `checkpoint_name` somewhere else first if you want to keep the shipped one, which is what both
notebooks do (they train into a scratch directory).

The browser demo — upload an image, pick one of the three shipped checkpoints, generate a caption —
is the unified frontend in `services/frontend`, not in this repo. All three checkpoints load
and generate captions.

Docker wraps the same entrypoints as two single-purpose Dockerfiles, both `FROM roshb/ai-residency-base-serve`:

```bash
# both images for this service, built from the repository root
make build SERVICE=multimodal-captioning
make push SERVICE=multimodal-captioning

# the whole stack, this service included
make -C deploy up

# train in a container
cd deploy && docker compose --profile train run --rm train-multimodal-captioning
```

`libs/common` is a private git dependency, so an image build needs a GitHub token. The Makefile
takes it from `gh auth token` and passes it as a BuildKit secret, mounted for one layer and never
written into the image. `checkpoints/` and `data/` are excluded from the build context and
bind-mounted at run time instead, so a container always serves whatever was most recently trained
rather than a snapshot baked in at build time. `train` is gated behind a Compose profile, so a
plain `docker compose up` never starts a training run by accident.

Underneath the `make` targets, these are the actual raw commands:

```bash
uv sync
uv run python -m multimodal_captioning.zero_shot      # Part 1
uv run python -m multimodal_captioning.training       # Part 2 — train the adapter
uv run python -m serving.api    # Part 2 — over HTTP
uv run jupyter notebook notebooks/notebook.ipynb                              # Part 2 — cell by cell
```

Inference picks its device through `ai_residency_common.get_device()` — CUDA, then Apple's MPS, then CPU.
Training deliberately does not: it pins CPU by default for reproducibility (Section 6).
Either way `make docker-*` is CPU-only here regardless, since Docker Desktop's Linux VM has no MPS
passthrough. Qwen3-0.6B-Base is small enough to hold alongside CLIP in a few GB of memory.
`Qwen/Qwen3-0.6B-Base` is a public model, so no Hugging Face token is strictly required to download
it, though setting `HF_TOKEN` avoids the anonymous-request rate limit.

## 6. Experimental Results

**Part 1 — CLIP zero-shot classification: 10/10.** Running `make zero-shot` against the real
`data/images/` set, every single image is classified correctly:

**Figure 8.** Real output — CLIP correctly labels all ten images with no training at all.
![CLIP zero-shot classification results](assets/clip_zero_shot.png)

This isn't surprising: CLIP was trained on this kind of task at a scale (400M image-text
pairs) far beyond anything else in this repo. But it's a genuinely working, from-scratch-run
zero-shot baseline, and a nice contrast to Part 2's much smaller-scale training.

**Part 2 — captioning.** The shipped default is `adapter_patches.pth`: 49 patch tokens, 4,000
Flickr30k training pairs, 15 epochs. Three earlier checkpoints also ship and still load — the
loader reads each one's architecture off the artifact — and they are what the scaling comparison
further down was run against.

**Captions are scored by CLIP agreement, not by held-out loss.** A frozen decoder can cut caption
loss by learning the *register* of Flickr30k sentences while describing the wrong picture. That is
not hypothetical here: an earlier patch-token run reached 2.2043 held-out loss against a 5.1933
untrained baseline while scoring *below* an untrained adapter on agreement. So `make evaluate`
embeds image and caption with CLIP and takes the cosine, with both reference points scored on the
same 200 held-out pairs — an untrained adapter as the floor, the captions a person wrote as the
ceiling.

| | CLIP agreement |
|---|---|
| untrained adapter | 0.1848 |
| **`adapter_patches.pth`** | **0.2115** |
| the captions a person wrote | 0.3233 |

That closes **19.2% of the floor-to-ceiling gap**. 87 of 100 captions are distinct, so the adapter
is responding to the image rather than emitting one sentence.

Scoring the generator's captions with the generator's own vision encoder flatters it: a caption can
agree with CLIP's view of the image without agreeing with the image. It is still the cheapest
signal that separates "describes this picture" from "reads like a caption", which loss does not.

**This does not isolate what the patch grid bought.** Against the 100-pair checkpoint, three things
changed at once: image tokens 1 → 49, training pairs 40x, epochs 5x. Attributing the gain to the
grid would mean training the single-token path at 4,000 pairs and 15 epochs too.

What it reliably describes is people and their clothing — the most common content in Flickr30k —
and much less of the rest of the scene:

| the caption a person wrote | the model's |
|---|---|
| These young ladies with one little girl are at a flea market purchasing items | a young girl in a white dress and a boy in a blue shirt and jeans. |
| A man without a shirt on is guiding a large brown horse pulling a green and yellow wagon. | a man in a white shirt and jeans, a man in a blue shirt and jeans, and a man in a black shirt… |
| Three boys are breaking up a pile of bricks, while four men are standing behind them. | a man in a white shirt and a man in a black shirt are standing in front of a building. |

The last row is the failure mode that remains: when the image is not mostly people, generation
falls back to a high-frequency sentence. Blocking repeated trigrams at decode time was measured
and does not help — agreement 0.2270 against 0.2266 — so decoding stays greedy and the limit is
the adapter, not the search.

The three earlier checkpoints load and generate through the UI, the API and both notebooks, using
greedy decoding, byte-identical across runs:

| Checkpoint | cat.jpg | dog.jpg | book.jpg |
|---|---|---|---|
| `adapter.pth` (10 pairs / 3 epochs) | "1999-2000 season. The team was the 1st team in the league. The team was the 1" | "1999-2000 season. The 1999-2000 season was the 10th" | "1999-2000 season. The team was the 1999-2000 season was the" |
| `adapter_trained.pth` (10 images / 20 epochs) | "]::::::::::::::::::::::::::..." | "::::::::::::::::::::::::::::..." | ":\n:\n:\n:\n:\n:\n:\n:\n:\n:\n..." |
| `adapter_flickr_batched.pth` (100 Flickr30k pairs / 3 epochs) | "The 2019-2020 season of the 2019-2020 season of the 20" | "The 2019-2020 season of the National Hockey League (NHL). The 2019-20" | "1999-2000 season. The team was the 1999-2000 season was the" |

**Figure 9.** The same results, alongside the actual input images.
![Caption generation across the three shipped adapter checkpoints](assets/caption_comparison.png)

At that training scale (100 pairs, 3 epochs, a ~1.58M-parameter adapter bridging a
596M-parameter frozen language model), captions stay fluent — Qwen3 free-associates confidently
regardless of what the adapter feeds it — but don't describe the images. `adapter_flickr_batched.pth`'s
captions vary by image where the least-trained checkpoint's barely do, a first sign the image token
was carrying information.

**Evaluation.** `multimodal_captioning/data.py` splits the sample 80/20, and training scores an
untrained adapter on the held-out half as a baseline before training starts. The shipped run:

```
Baseline (untrained adapter) held-out loss: 5.1933
Epoch  1/15  train_loss=2.5658  val_loss=1.9971
Epoch  5/15  train_loss=1.8993  val_loss=1.9227
Epoch 10/15  train_loss=1.8491  val_loss=1.8851
Epoch 15/15  train_loss=1.7899  val_loss=1.8589
Best held-out loss 1.8589 against baseline 5.1933 (beats baseline)
```

Epoch counts are an upper bound rather than a plan — `BestMetric` stops a run after three epochs
without a new best. It never fired here: held-out loss was still falling at epoch 15, so 15 was a
budget, not a converged curve. Read that loss next to the agreement table above, not on its own.

**Data alone moves this very little, which is why the image representation was the thing to
change.** The [published post](https://roshbeed.com/posts/2026-06-29-image-captioning/) measures
"more data and epochs" directly: the same single-token adapter at 1,600 Flickr30k pairs, sixteen
times the largest checkpoint above, scored the same way.

| | CLIP agreement |
|---|---|
| untrained adapter | 0.1882 |
| trained, three seeds | 0.2007 / 0.2092 / 0.2276 |
| the captions a person wrote | **0.3280** |

That is 8.6%, 12.6% and 28.2% of the gap to human captions — a mean gain of 0.0228 whose spread is
wider than two of the three gains. Sixteen times the data moves it, and the move is both small and
unstable. Those numbers are the notebook's, not a shipped checkpoint's, and its floor and ceiling
(0.1882 and 0.3280) differ slightly from the shipped run's (0.1848 and 0.3233) because the two
scored different held-out clips. Compare the fractions of the gap, not the raw agreements.

**Training runs on CPU** (`Config.train_on_cpu = True`) for reproducibility — the backward pass
over the frozen 596M-parameter decoder isn't deterministic on MPS across runs, while CPU runs are
byte-identical. Inference still uses `get_device()` (CUDA/MPS/CPU), since a forward-only pass is
deterministic on MPS. This follows precedent elsewhere in the portfolio: the dual-encoder retrieval
project's GRU tower and the vision transformer project's classifier trainer are CPU-only too.
